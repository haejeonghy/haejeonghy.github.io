## 들어가며

요즘 트렌드는 **계산 중심**보다 **데이터 중심** 애플리케이션으로 이동하고 있다.

## 좋은 시스템의 조건

- **신뢰성** — 기대하는 대로 동작한다. 여기서 중요한 개념이 **Systematic Error(체계적 오류)** 인데, 무작위로 발생하는 오류와 달리 **일관된 방향으로 반복 발생하는 오류**를 말한다. 예를 들어 잘못된 설계 가정이나 결함 있는 로직에서 비롯된 버그가 이에 해당한다. 신뢰성 있는 시스템은 이런 체계적 오류를 설계 단계에서부터 방지해야 한다.
- **확장성** — 증가한 부하에 대해 시스템이 감당할 수 있는 능력
- **유지보수성**

### 소프트웨어 설계 3원칙

- **운용성** — 운영이 원활하게 이루어질 것 → 자동화
- **단순성** — 엔지니어가 이해하기 쉬울 것 → 추상화
- **발전성** — 쉽게 변경할 수 있을 것

## 데이터 모델과 질의 언어

데이터 모델은 그 위에서 동작하는 소프트웨어가 **할 수 있는 일과 없는 일**에 지대한 영향을 미친다.

### 관계형 모델 (SQL)

- 정규화된 구조, 데이터 저장·질의, 비즈니스 데이터 모델에 특화
- **쿼리 옵티마이저**가 실제 접근 경로를 결정해주므로, 애플리케이션에서 접근 경로를 따로 고민할 필요가 없음
- 외래키(Foreign Key)로 관계를 표현

### 문서형 모델 (NoSQL)

- 높은 쓰기 처리량, 뛰어난 확장성
- 스키마 유연성, 저장소 지역성, 질의가 간단한 경우에 유리
- JSON을 활용하면 애플리케이션 객체와 데이터 구조 간 불일치를 줄일 수 있음
- 문서 모델에서 관계는 **문서 참조(Document Reference)** 라고 부름

#### 객체-관계형 불일치 (Object-Relational Mismatch)

- 애플리케이션의 객체 모델과 데이터베이스 모델 사이에 불일치가 존재
- ORM이 보일러플레이트 코드를 줄여주지만, 근본적인 불일치를 완전히 숨길 수는 없음

#### 문서 모델이 적합한 경우

- 애플리케이션 데이터가 문서와 유사한 구조일 때 (일대다 트리 관계, 전체 트리를 한 번에 적재)
- 애플리케이션이 자주 전체 문서에 접근할 때 → **저장소 지역성(Storage Locality)** 으로 성능 이점

#### 문서 모델의 한계

- 중첩 항목을 직접 참조할 수 없음
- **다대일, 다대다 관계**에 취약 — 조인 지원이 미흡하기 때문
- 특정 시점에 발생한 이벤트를 기록하는 분석 애플리케이션에는 적합하지 않을 수 있음

### 스키마 유연성 — 암묵적 스키마

문서 데이터베이스는 스키마가 없는 것이 아니라, **암묵적 스키마**가 있지만 데이터베이스가 이를 강요하지 않는다.

- 임의의 키와 값을 문서에 추가할 수 있고, 읽을 때 특정 필드의 존재를 보장하지 않음
- 예시: 전체 이름을 하나의 필드에 저장하다가 성/이름으로 분리하고 싶다면
  - 문서 DB → 새 필드를 가진 문서를 작성하고, 이전 문서를 읽을 때 처리하는 코드만 추가하면 됨
  - 정적 타입 RDBMS → 스키마 마이그레이션 필요, MySQL의 경우 변경 시 수 분~수 시간의 서비스 중단이 발생할 수 있음
- 모든 레코드가 동일한 구조를 가져야 한다면 스키마는 문서화와 구조 강제를 위한 **유용한 메커니즘**이 됨

> Oracle은 **다중 테이블 색인 클러스터 테이블(Multi-table Index Cluster Table)** 기능으로 관계형 모델에서도 저장소 지역성과 유사한 특성을 제공한다. 이 기능은 서로 관련 있는 여러 테이블의 데이터를 물리적으로 같은 위치(같은 디스크 블록)에 저장해, 함께 조회되는 데이터를 한 번의 I/O로 읽을 수 있게 해준다. 즉, 문서 DB의 지역성 이점을 관계형 DB에서도 누릴 수 있게 하는 방법이다.

### 관계형 vs 문서형의 수렴

관계형 데이터베이스와 문서 데이터베이스는 시간이 지남에 따라 점점 더 비슷해지고 있다. 각자 부족한 부분을 서로 보완해나가고 있기 때문이다.

## 데이터를 위한 질의 언어

### 명령형 언어

특정 순서로 특정 연산을 수행하도록 컴퓨터에 직접 지시한다.

### 선언형 언어 (SQL, 관계 대수 등)

- 목표를 달성하는 방법이 아닌, **알고자 하는 데이터의 패턴**과 조건만 지정
- 더 간결하고 다루기 쉬움
- DB 엔진의 상세 구현이 숨겨져 있어, **질의를 변경하지 않고도 DB 성능을 향상**시킬 수 있음
- SQL은 순서가 달라져도 결과가 같음 → 기능적 제한이 오히려 **자동 최적화 여지**를 넓혀줌
- **병렬 실행에 적합**

### 맵리듀스 (MapReduce)

- 많은 컴퓨터에서 대량의 데이터를 처리하기 위한 프로그래밍 모델
- 질의 로직은 처리 프레임워크가 반복적으로 호출하는 조각 코드로 표현됨
- `map`과 `reduce` 함수는 **순수 함수**여야 하고, 사이드 이펙트가 없어야 함
- 클러스터 환경에서 분산 실행을 위한 저수준 프로그래밍 모델
- MongoDB는 이를 보완하기 위해 **집계 파이프라인(Aggregation Pipeline)** 이라는 선언형 질의 언어를 지원함. 집계 파이프라인은 데이터를 여러 단계(stage)에 걸쳐 순차적으로 변환·집계하는 방식으로, `$match`(필터링) → `$group`(그룹화) → `$sort`(정렬) 같은 단계를 파이프처럼 연결해 사용한다. MapReduce보다 훨씬 간결하고 최적화하기도 쉬움

## 그래프형 데이터 모델

다대다 관계가 복잡하게 얽혀 있을 때 적합한 모델.

그래프는 두 가지 객체로 이루어진다:

- **정점 (Vertex)** — 고유 식별자, 유출 간선 집합, 유입 간선 집합, 속성 컬렉션(키-값 쌍)
- **간선 (Edge)** — 고유 식별자, 꼬리 정점(시작), 머리 정점(끝), 관계 유형 레이블, 속성 컬렉션(키-값 쌍)

그래프 위에서 동작하는 다양한 알고리즘이 있다 (예: 최단 경로 알고리즘 등).

### 속성 그래프 모델과 Cypher

- **Cypher** 는 속성 그래프를 위한 **선언형 질의 언어**
- 수행 방법을 자세히 지정할 필요 없이, 질의 최적화기가 가장 효율적인 전략을 자동으로 선택
- SQL로도 그래프 질의가 가능하지만 **재귀 공통 테이블 식(Recursive CTE)** 을 사용해야 하며, Cypher에 비해 문법이 어렵고 길고 복잡함
- 그래프 모델은 데이터 모델링에 있어 **높은 유연성**을 제공함

### 트리플 저장소 모델

- 그래프 모델과 거의 동등하지만, 다른 용어를 사용해 같은 개념을 설명
- 모든 정보를 **(주어, 서술어, 목적어)** 세 부분 형식으로 저장

### 시맨틱 웹 (Semantic Web)

- 웹사이트가 사람이 읽을 수 있는 정보뿐 아니라, **컴퓨터가 읽을 수 있는 기계 판독 가능 데이터**도 제시하자는 개념
- 현재는 부정적인 평가가 많음

### SPARQL

- **RDF(Resource Description Framework) 데이터 모델**은 웹 자원 간의 관계를 표현하기 위한 W3C 표준으로, 모든 정보를 **(주어, 서술어, 목적어)** 트리플 형태로 나타낸다. 예를 들어 "서울은 대한민국에 위치한다"를 `(서울, 위치한다, 대한민국)` 으로 표현하는 식이다. 트리플 저장소는 이 RDF 모델을 기반으로 데이터를 저장한다.
- **SPARQL**은 이 RDF 데이터 모델을 사용하는 트리플 저장소의 질의 언어
- RDF는 속성과 간선을 구별하지 않고 **서술어만 사용**하여, 속성 매칭에도 동일한 구문을 사용할 수 있음

### 데이터로그 (Datalog)

- 일부 데이터 시스템에서 사용되는 보다 일반화된 질의 언어
- 서술어(predicate)로 작성
- 단계를 나눠 한 번에 조금씩 질의로 나아감
- 새로운 서술어를 정의하는 규칙을 데이터베이스에 전달
- 다른 질의의 규칙을 **결합하거나 재사용**할 수 있어 매우 강력한 접근 방식

## 저장소와 검색

애플리케이션 개발자는 저장소 엔진을 처음부터 직접 구현하기보다는, 사용 가능한 여러 저장소 엔진 중에서 **애플리케이션에 적합한 엔진을 선택**하는 작업이 필요하다.

### 데이터베이스를 강력하게 만드는 데이터 구조

많은 데이터베이스는 내부적으로 **추가 전용(append-only) 데이터 파일인 로그**를 사용한다.

### 색인 (Index)

색인은 기본 데이터에서 파생된 **부가적인 메타데이터 구조**다.

- 색인을 잘 선택했다면 **읽기 질의 속도가 향상**되지만, 모든 색인은 **쓰기 속도를 떨어뜨린다**
- 오버헤드를 최소화하면서 애플리케이션에 가장 큰 이익을 주는 색인을 수동으로 선택할 수 있다

#### 키-값 색인과 해시 인덱스

- 키-값 데이터는 매우 일반적이고, 복잡한 색인을 위한 구성 요소이기도 함
- 가장 간단한 색인 전략 → **키를 데이터 파일의 바이트 오프셋에 매핑한 인메모리 해시 맵**을 유지하는 것
- 파일에 새로운 키-값 쌍을 추가할 때마다 해시 맵도 갱신해야 함
- 파일에 계속 추가만 하면 디스크 공간이 부족해지는 문제 → **세그먼트 분리**로 해결
  - 특정 크기에 도달하면 세그먼트 파일을 닫고, 이후 쓰기는 새로운 세그먼트 파일에 수행
  - **컴팩션(Compaction)** 수행 가능 — 로그에서 중복된 키를 버리고 각 키의 최신 값만 유지하는 것. 세그먼트를 더 작게 만들어 여러 세그먼트 병합이 가능하고, 컴팩션 수행 중에도 이전 세그먼트를 이용해 읽기·쓰기를 정상적으로 처리할 수 있음
- 해시 테이블은 **범위 조회에 비효율적** — 키 순서를 보존하지 않아 랜덤 위치에 저장되기 때문

### SS테이블과 LSM 트리

#### SS테이블 (Sorted String Table)

키-값 데이터를 **키 기준으로 정렬해서 저장**한 파일 형식.

- 큰 파일도 쉽게 병합 가능
- 메모리 인덱스를 크게 만들 필요 없음
- 블록 압축 가능

#### Memtable과 SS테이블 생성 흐름

쓰기가 발생하면 바로 디스크에 저장하는 것이 아니라, 먼저 **메모리 내 정렬 자료구조인 Memtable**에 쌓인다. Memtable이 일정 크기에 도달하면 SS테이블 파일로 디스크에 플러시(flush)된다.

- Memtable의 단점 → 서버가 죽으면 아직 플러시되지 않은 데이터가 **손실**될 수 있음 (별도의 WAL로 보완)

#### LSM 트리 (Log-Structured Merge Tree)

Memtable + SS테이블 구조를 기반으로 한 저장소 엔진.

- 백그라운드에서 연쇄적으로 SS테이블을 지속적으로 병합
- 데이터가 정렬된 순서로 저장되어 **범위 질의를 효율적으로 실행** 가능
- 디스크 쓰기가 순차적이라 **매우 높은 쓰기 처리량** 보장
- SS테이블 압축·병합 순서와 시기를 결정하는 전략으로 **크기 계층(Size-Tiered)** 과 **레벨 컴팩션(Leveled Compaction)** 이 있음
- 키 조회 시 Memtable 확인 후 존재하지 않으면 가장 오래된 세그먼트까지 거슬러 올라가야 하는 문제 → **블룸 필터(Bloom Filter)** 를 추가로 사용해 불필요한 탐색을 줄임

### B트리 (B-Tree)

SS테이블과 마찬가지로 **키로 정렬된 키-값 쌍**을 유지하며, 키-값 검색과 범위 질의에 효율적이다.

- 전통적으로 **4KB 크기의 블록(페이지)** 단위로 나누고, 한 번에 하나의 페이지를 읽거나 씀 → 하드웨어 구조와 밀접한 관련
- 한 페이지가 B트리의 루트 역할을 하며, 탐색을 따라가면 최종적으로 개별 키를 포함하는 리프 페이지에 도달

#### B트리의 읽기·쓰기 동작

- **값 갱신** → 키를 포함한 리프 페이지를 검색 → 값을 바꾼 뒤 디스크에 다시 기록
- **키 추가** → 해당 범위의 페이지를 찾아 키-값을 추가. 페이지에 여유 공간이 없으면 페이지를 둘로 나누고 상위 페이지를 갱신
- 기본 쓰기 동작은 디스크 상의 페이지를 **덮어씀** → LSM 트리의 추가 전용 방식과 대조적

#### 쓰기 전 로그 (WAL, Write-Ahead Log)

페이지를 덮어쓰는 도중 고장이 발생하면 데이터가 손상될 수 있다. 이를 방지하기 위해 **트리 페이지에 변경을 적용하기 전에 모든 변경 사항을 WAL에 먼저 기록**한다. 고장 이후 복구 시 WAL을 사용해 B트리를 일관성 있는 상태로 복원한다.

#### B트리 최적화 기법

- WAL 대신 **쓰기 시 복사(Copy-on-Write)** 방식 사용
- 페이지에 전체 키를 저장하는 대신 **키를 축약**해서 저장 → 페이지당 더 많은 키를 담을 수 있음
- **리프 페이지를 디스크 상에 연속된 순서**로 배치하려 시도 (LSM 트리는 병합 과정에서 자연스럽게 연속성이 유지되는 반면, B트리는 별도 노력이 필요)
- 트리에 **포인터 추가** (예: 형제 페이지 포인터)

### B트리 vs LSM 트리 비교

- **구현 성숙도** — B트리가 더 높음. LSM 트리도 성능 특성 덕분에 관심이 높아지고 있음
- **쓰기 성능** — LSM 트리가 유리. 순차 쓰기 기반이라 디스크 I/O가 효율적
- **읽기 성능** — B트리가 유리. LSM 트리는 읽기 시 여러 컴팩션 단계의 SS테이블을 모두 확인해야 하기 때문에 상대적으로 느림

### LSM Tree와 B-Tree의 근본적인 트레이드오프

- 저장소 엔진 설계는 결국 **디스크 I/O 비용을 어디에 배분할 것인가**의 문제다.
- B-Tree
  - 랜덤 쓰기가 발생하지만 **읽기 latency가 안정적**이다.
  - point lookup, range query, OLTP workload에 적합하다.
- LSM Tree
  - 랜덤 쓰기를 **순차 쓰기(append)**로 바꿔 **write throughput을 높인다.**
  - 대신 read amplification, compaction 비용이 발생한다.
- 따라서 데이터베이스 선택은 단순히 “읽기 vs 쓰기”가 아니라 다음을 고려해야 한다.
  - read/write ratio
  - latency 요구사항
  - range query 필요 여부
  - 데이터 변경 패턴

### LSM Tree에서 SSTable이 정렬되어 있어야 하는 이유

- SSTable은 항상 **key 기준 정렬된 상태**로 저장된다.
- 이유
  - compaction 시 **O(n) merge 가능**
  - range query 지원
  - sparse index 생성 가능
- 정렬되지 않았다면 compaction마다 전체 정렬이 필요해 비용이 크게 증가한다.

### Compaction의 역할과 비용

- LSM Tree는 append-only 구조이기 때문에 동일 key의 여러 버전이 존재한다.
- compaction은 다음 작업을 수행한다.
  - 최신 value만 유지
  - tombstone 정리
  - SSTable 개수 감소
- compaction이 없으면
  - read 시 확인해야 할 SSTable이 계속 증가
  - read amplification 증가
- 하지만 compaction은
  - 대량 disk read/write
  - write amplification
    을 발생시킨다.

### LSM Tree의 세 가지 Amplification

- 저장소 엔진 설계에서 중요한 개념
- read amplification
  - 데이터를 읽기 위해 여러 위치를 확인해야 하는 현상
- write amplification
  - 논리적 write 1번이 실제 디스크 write 여러 번으로 증가
- space amplification
  - 실제 데이터보다 더 많은 디스크 공간 사용
- compaction 전략은 이 세 가지 사이의 trade-off를 조정한다.

### Compaction 전략

- Size-tiered compaction
  - 비슷한 크기의 SSTable을 묶어 merge
  - write amplification이 낮다
  - read amplification이 증가할 수 있다
  - 예: Apache Cassandra
- Leveled compaction
  - level 구조로 관리하며 key range가 겹치지 않게 유지
  - read 성능이 안정적
  - write amplification이 증가
  - 예: RocksDB, LevelDB

### Tombstone과 Lazy Deletion

- LSM Tree에서는 delete 시 데이터를 바로 삭제하지 않는다.
- 대신 tombstone 레코드를 기록한다.
- 이유
  - SSTable은 immutable이기 때문에 기존 파일을 수정할 수 없다.
  - 동일 key가 여러 SSTable에 존재할 수 있다.
- 실제 삭제는 compaction 시 수행된다.
- tombstone이 많아지면
  - range query 비용 증가
  - compaction 부담 증가

### Bloom Filter의 역할

- Bloom filter는 특정 SSTable에 **key가 존재하지 않음을 빠르게 판단**하기 위해 사용된다.
- 특징
  - false positive 가능
  - false negative 없음
- 디스크 접근을 줄여 read 성능을 개선한다.

### OLTP와 OLAP의 차이

- OLTP (Online Transaction Processing)
  - 짧은 query
  - 높은 동시성
  - 낮은 latency 요구
  - point lookup 중심
- OLAP (Online Analytical Processing)
  - 대량 데이터 scan
  - aggregation 중심
  - 분석 workload
- 대부분 서비스는
  - OLTP DB (서비스)
  - OLAP 시스템 (분석)
    구조를 함께 사용한다.

### Event Log와 State Store

- Event log
  - 사건(event)의 기록
  - append-only
  - immutable
- State store
  - 현재 상태를 저장하는 데이터베이스
- 구조 
  `event log → processing → state store`
- event는 history
- state는 계산된 결과(snapshot)

### Event Log가 Source of Truth가 되는 이유

- event는 **사실(fact)**의 기록이다.
- 상태는 이벤트를 replay하여 재구성할 수 있다. 
  `state = replay(events)`
- 장점
  - audit 가능
  - 시스템 복구 가능
  - 여러 서비스가 동일 이벤트 사용 가능

### Append-only 구조의 장점

- immutable 데이터 구조
- 동시성 충돌 감소
- sequential write로 디스크 효율 증가
- 시스템 복구가 쉬움
- 대표 사례
  - Kafka
  - LSM storage engine
  - Git

### Event System에서 Schema Evolution

- 이벤트는 immutable이므로 기존 이벤트를 수정하지 않는다.
- schema 변경 시
  - version 관리
  - consumer에서 backward compatibility 처리
- 문제
  - 이벤트 버전이 많아질수록 consumer 복잡도 증가

### Event Log와 데이터 삭제 문제

- 이벤트는 원칙적으로 immutable이다.
- 그러나 개인정보 규제(GDPR 등) 때문에 삭제 요구가 발생한다.
- 해결 전략
  - PII를 이벤트에 저장하지 않음
  - 암호화 후 키 삭제 (crypto shredding)
  - 데이터 익명화
  - log compaction

### Event-driven 아키텍처의 핵심 규칙

- event log가 source of truth라면 항상 다음 순서를 지켜야 한다. 
  `event → event log → state update`
- state가 먼저 변경되면
  - event replay 시 상태 재구성이 불가능해진다.
  - state와 event history가 불일치하게 된다.

### Event 기반 시스템에서 Ordering이 중요한 이유

- 이벤트는 시간 순서대로 상태를 변화시킨다.
- 순서가 깨지면 상태 계산이 잘못된다.

예 
`deposit 100` 
`withdraw 50`

순서가 바뀌면 
`withdraw 50` 
`deposit 100`

결과 상태가 달라질 수 있다.

- 그래서 Kafka 같은 시스템은 **partition ordering**을 강하게 보장한다.

### 아키텍트 관점에서 기억할 핵심 문장

- **Database = materialized view of a log**
- event는 사실의 기록
- state는 계산된 결과
- 저장소 엔진 설계는 결국 **I/O 비용 분배 문제**다.
